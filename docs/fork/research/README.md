# Research: measuring and extending gbrain retrieval

*Gabriel Kpodoh, with Claude (Anthropic). October 2026.*

This folder documents retrieval research done on a fork of [gbrain by Garry Tan](https://github.com/garrytan/gbrain). gbrain is Garry Tan's project; this fork measured its search on one real brain, fixed what the measurements pointed to, and tested a few extensions. The full write-up is [gbrain-2.0-paper.md](gbrain-2.0-paper.md).

## What was asked

Can Claude find the right page in a personal brain, and answer multi-step questions from it? The brain is the author's work brain: about 1,160 pages (meeting notes, chat threads, project, system, process and person pages, personal reflections), about 3,780 chunks and 6,950 graph links, mostly in French. It ran gbrain 0.48.1, then 0.60.340 from 21 October 2026.

One constraint shaped everything: "gbrain indexes, Claude reasons". gbrain never writes knowledge itself; its OpenAI key serves embeddings only, and anything that writes or reasons goes through Claude. So every gbrain feature that relies on gbrain's own chat model was off.

## Method

- **Question benches** in the native qrels format: v2 (107 questions, half of them real queries taken from Claude Code sessions) for tuning, holdout A (41) for validation, holdout B (41) opened once. No question is shared.
- **Metrics:** Recall@5, MRR, nDCG@5 with `gbrain eval --qrels`.
- **End-to-end bench:** 22 multi-step questions answered by Claude Sonnet with read-only gbrain tools, judged by Claude Haiku against verified reference answers.
- **Targeted benches** built for each track: 40 questions whose answer sits in one middle chunk of a long page; 20 overview questions with verified expected elements.
- **Isolated labs:** each track ran on a fresh native lab brain (`gbrain init --db-only`, content imported from a snapshot, graph links copied). Paired bootstrap confidence intervals for every comparison.
- **Rule:** nothing goes live without a measurement on the tuning bench and a holdout.

## Headline results

Recall@5 / MRR / nDCG@5.

| Bench | Start (0.60, original config) | Final configuration |
|---|---|---|
| v2 (107, tuning) | 0.68 / 0.60 / 0.58 | **0.92 / 0.86 / 0.85** |
| Holdout A (41, validation) | 0.85 / 0.76 / 0.75 (reranker alone) | **0.91 / 0.84 / 0.83** |
| Holdout B (41, opened once) | — | **0.92 / 0.89 / 0.88** |
| Targeted middle-chunk bench (40) | 0.57 / 0.51 / 0.53 | **0.78 / 0.70 / 0.72** with doc2query live |

The two largest gains were diagnoses, not additions:

1. **Slug-prefix boosts tuned for another brain.** gbrain multiplies similarity by ×1.5 for `originals/` pages. In this brain those are 171 short, abstract reflections, and they crowded out factual pages. Turning the boosts off: v2 recall from 0.68 to 0.86 without a reranker.
2. **The reranker replaced the hybrid order instead of complementing it.** Jev and the hybrid search miss different questions (7 each on v2). Fusing the two orders by RRF (k = 20): +8 recall points and +9 MRR points.

## What shipped

| Change | Effect |
|---|---|
| Slug-prefix boosts off (`search.source_boosts = none`) | Largest single gain |
| TypeSafe Jev reranker, fused with the hybrid order, page title passed to it, scoring rubric spelled out | v2 0.86 / 0.73 / 0.73 → 0.92 / 0.86 / 0.85 |
| 56 rewritten titles, French full text | Small gains without a reranker |
| **doc2query**: 3 to 5 questions per chunk of long pages, generated by Claude Haiku via `claude -p`, stored in a `chunk_index_text` table, added to the embedding and full text behind `search.chunk_index_text = d2q` (off by default, byte-identical when off) | Targeted bench 0.57 / 0.51 / 0.53 → 0.78 / 0.70 / 0.72; v2 unchanged at 0.92 / 0.84 / 0.84; no added latency; about $2.40 for the full build |
| **Supersession "annotate"**: `superseded_by` frontmatter on stale pages, reported in results, order unchanged | Stale page leaves the agent's citations on the known failure; benches identical |
| Weekly read-only stale-page detection (embedding neighbours, judged by Claude Sonnet, confirmed by Claude Opus) | 8 reliable pairs out of 799 candidates; proposals only |
| Health report, weekly bench, capture of real searches, night hygiene by Claude | Regression watch |

## What was dropped, and why

| Idea | Result | Why |
|---|---|---|
| Query expansion | 0.85 / 0.74 / 0.73 vs 0.86 / 0.73 / 0.73, +5 s per search | No gain |
| Anthropic-style per-chunk context, on 2,513 chunks | +0.02 MRR on the targeted bench, within noise | It describes the page, which titles already do; doc2query fixes the failure instead |
| Autocut | No effect on the metrics | Shortens lists, nothing more |
| Demoting superseded pages | Neutral (penalty) to harmful (substitution) | A stale page is still the right answer for questions about its history |
| Thematic summaries + router | Per-element judge +0.07 / +0.08, intervals include 0 | Overview requests are rare: 3 real ones in two months |
| Iterative-search instructions for the agent | 0.43 and 0.50 vs 0.57 for no instruction | No gain |
| Strategy routing (Adaptive-RAG style) | Oracle over strategies 0.77; best of three runs of the same strategy 0.89 | No headroom: remaining errors are run-to-run variance and content |

On the end-to-end bench, the base agent scored 0.57 on 21 October (one run, before the changes) and 0.75 and 0.77 on 23 October with the changes live. That comparison is confounded: the brain's content changed between the two dates.

## How to reproduce

The benches reference pages of a private brain, so to reproduce you need your own question sets. The scripts are general:

1. **Write qrels for your brain** in the native format: questions with their expected pages. Keep a tuning set and at least one holdout you open once. Mix real queries from your agent's logs with written ones.
2. **Measure a configuration** with `gbrain eval --qrels <file> --limit 10 --k 5`. `ops/eval/run-bench.sh` wraps it to compare configurations (no reranker, reranker alone, fusion) and restores the configuration on exit.
3. **Measure answers end to end** with `ops/eval/agentic/run.py` (Claude answers with read-only gbrain tools) and `ops/eval/agentic/judge.py` (Claude Haiku judges against references). Run each variant at least twice: on 22 questions, run-to-run variance is large.
4. **Test index changes in a lab brain**, never in a `pg_restore` copy, which keeps the live brain's write binding. Create a fresh one with `gbrain init --db-only`, import a snapshot, copy the graph links.
5. **Track scripts:** `ops/eval/chunk/` (targeted bench, six index states, bootstrap intervals), `ops/eval/truth/` (stale-page detection, supersession variants), `ops/eval/router/` (frequency count, overview bench, router accuracy), `ops/doc2query/` (generation and import for the live doc2query index).
6. **Run `claude -p` with `--strict-mcp-config`** and an empty MCP config, otherwise it loads your MCP servers and prompts become too long. Budget your Claude quota and your reranker calls before running parallel benches.

Limits worth keeping in mind: one brain, labels that miss some relevant pages, an automatic judge, and a saturated machine during part of the measurements. They are listed in §6 of the paper.
